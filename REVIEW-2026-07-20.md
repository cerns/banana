# Codebase Consistency Review — 2026-07-20

Full-codebase review for inconsistencies and unclear behavior, run with three
parallel reviewers (prompt-path consistency, docs-vs-code drift, naming/dead
code). Findings verified against source with file:line references.

Context: this review was commissioned ahead of a planned feature — a global
"chat only" system prompt so agents never present interactive choice menus and
instead ask questions as plain-text bullets. Section D describes the design;
Section A explains why naive implementation would silently fail.

---

## A. Prompt/option delivery inconsistencies (behavioral)

The three `SshRunOptions` fields (`bare`, `systemPrompt`, `maxTurns`) are
honored ONLY on the SSH `--print` path for remote machines. Summary matrix:

| Option        | --print remote | --print local | tmux (persistent) |
|---------------|----------------|---------------|-------------------|
| bare          | yes (sshRunner.ts:741) | dropped | only via `suffix==='-hub'` coincidence (tmuxRunner.ts:757) |
| systemPrompt  | yes (sshRunner.ts:790-802) | dropped | dropped |
| maxTurns      | yes (sshRunner.ts:759) | dropped | dropped |
| auto-compact  | yes (remoteSessionExecutor.ts:291-332) | yes | never |
| --resume      | every job | every job | first-create only |
| model         | every job | every job | first-create only |

1. **tmux branch drops sshOpts entirely.** `runJob` never forwards `sshOpts`
   into `runClaudeViaTmuxForSession` (remoteSessionExecutor.ts:241-261); the
   function signature has no parameter for it. In persistent-tmux mode (the
   mode used on enterprise plans) NO system prompt, role prompt, SKIP
   guidance, or turn cap ever reaches the agent. The entire B1/B3 prompt
   architecture functions only in --print mode.
2. **Local machines drop all three options even in --print mode.**
   `runClaudeLocally` (sshRunner.ts:556-581) accepts only
   resumeId/signal/model; never adds --bare/--append-system-prompt/--max-turns.
3. **--bare reaches tmux only by coincidence** via `suffix === '-hub'`
   (tmuxRunner.ts:757-758), not from `sshOpts.bare`. Any new exec channel
   would diverge silently.
4. **tmux sessions never auto-compact** and never record `lastInputTokens`
   (auto-compact lives only in the --print branch,
   remoteSessionExecutor.ts:291-332, 363-373).
5. **`continueTalking` dispatches with NO sshOpts at all** (hubRouter.ts:1198)
   — talking continuations run uncapped, un-bare, with no system prompt and
   none of the global rules (it builds its own guidance from scratch,
   hubRouter.ts:1156-1176, omitting ONE-EXECUTOR / NO-TOOL-USE / BE-BRIEF).
6. **Direct API sends are uncapped** (apiRouter.ts:529 — no sshOpts).
   **Compaction/summarizer runs are uncapped** (hubRouter.ts:1714, 2002) and
   also bypass `createJob`, so this LLM work never appears in job history.
7. **Triggered dispatches get no system prompt** — sshOpts is
   `{ maxTurns }` only (hubRouter.ts:884-890); identity/guidance live solely
   in the user prompt.
8. **No single hook reaches every execution path.** The only text channel
   that reaches all paths today is the user `prompt` string built in
   `dispatchToSession` / `continueTalking`.

### Prompt-text contradictions

9. `buildGuidance('triggered')` (hubRouter.ts:608-636) concatenates
   `globalRules` with text that contradicts them:
   - RULE 4 "NO TOOL USE IN CHAT … No Read, Edit, Write, Bash" (:597) vs
     triggered "Use Read / Edit / Write … Use Bash" (:615-618).
   - RULE 5 "SKIP AGGRESSIVELY … reply `[SKIP][#reason]` only" (:601) vs
     triggered "Do NOT respond with `[SKIP]`" (:635).
   - RULE 1 "BE BRIEF: 2-5 sentences" (:587) vs the multi-part work-report
     format (:623-625).
10. Comment at hubRouter.ts:816-817 says triggered prompts need no reply tags
    (banana auto-posts), but `buildGuidance('triggered')` instructs wrapping
    output in `[CHANNEL_REPLY]…[/CHANNEL_REPLY]` (:627-633). Both are sent.
11. SKIP instructions phrased five different ways (hubRouter.ts:601, 605,
    659, 678, 1164; plus "do NOT SKIP" :635). Parser tolerates all; the
    instruction text is inconsistent.
12. "Do NOT ask the user clarifying questions" exists ONLY in triggered
    guidance (:635). Chat/listen/talking agents are never told — this is why
    choice menus appear in chat at all.
13. Interactive-question handling differs by path: tmux auto-resolves choice
    menus at runtime (tmuxRunner.ts choice-menu block; AskUserQuestion in
    KNOWN_TOOL_NAMES); --print has no equivalent — a menu just becomes the
    reply text.
14. Stale doc comment: sshRunner.ts:700 says `--append-system-prompt-file`;
    implementation uses `--append-system-prompt` (:790, :802).

## C. Naming, duplication, dead code

23. "session" means three things (banana SessionRecord, claude conversation
    via claudeSessionId/resumeId, tmux session) and logs mix them freely.
24. Same exec-target spelled `hub-channel:` (ExecChannel union) vs `hub-ch-`
    (exec keys + tmux suffixes); `tmuxSuffixForKey` hand-slices between the
    two. "suffix" vs "slug" vocabulary split across three helpers.
25. Screen-name fallback chains diverge: server `screenName ?? name ??
    sid.slice(0,8)`; push notifications `name ?? machine.alias` (no
    screenName); dashboard `labelFor` uses `||` and slice(0,6) (app.js:1977)
    while hub pickers use slice(0,8) inline (app.js:2154,2210,2219); session
    list drops screenName entirely (app.js:492).
26. `createRemoteSession` sets `hostname: name` (sessionManager.ts:34) so the
    dashboard renders the same string twice (app.js:525 + :533).
27. tmux-name grammar exists in three independent copies: tmuxRunner.ts:646,
    remoteSessionExecutor.ts:40, and hardcoded dashboard strings
    (app.js:512-517).
28. `fmtDuration` implemented three times (executor, app.js:1094, and
    app.js:1521 `fmtElapsed` with different rounding).
29. API error shapes inconsistent: mostly `{error}`, one endpoint
    `{ok:false, error}` (apiRouter.ts:218), one `{steps, error}` (:257).
    Success is uniformly `{ok:true,...}`; failure shape is not relied-upon.
30. Module-loading mix: `require()` at remoteSessionExecutor.ts:501 and
    tmuxRunner.ts:73 vs `await import()` everywhere else.
31. Dead local var + near-miss bug: sshRunner.ts:123 computes an `escaped`
    string identical to shellEscape but line 124 uses raw `${content}`.
32. Two queues with blurred naming: `SessionRecord.hubQueue` (persisted hub
    message ids, drained by hubRouter processQueue/drainGlobalQueue) vs
    executor `pendingQueue` (in-memory created jobs per exec key, drained by
    drainSessionQueue). Comments describe them with vocabulary matching
    neither variable name (remoteSessionExecutor.ts:413-416, :47 vs :423).
33. Possibly-dead exports (VERIFY AGAINST TESTS FIRST — many exports like
    classifyStartupScreen/hasTmuxSession/isPromptLine are intentional test
    seams imported by test files): runClaudeViaTmux (tmuxRunner.ts:1408),
    compactOutput (hubRouter.ts:1991), getPendingJobCount
    (remoteSessionExecutor.ts:129), isSkipResponse wrapper (hubRouter.ts:782).
34. Duplicate import of remoteSessionExecutor.js in index.ts (:11 and :19).
35. localStorage keys: fully consistent (all `banana_`-prefixed, all
    read+written). JobSource values: set consistently everywhere; only gap is
    compaction runs bypassing createJob (see finding 6).

## D. Planned feature: global "chat only — no choice menus" prompt

Goal: agents never present numbered options/menus/choice sets; when input is
needed they ask short plain-text questions as bullets in their reply and
proceed on reasonable assumptions if unanswered.

Design (informed by Section A):

1. **Plumb system prompts into tmux first** — pass a launch-time
   `--append-system-prompt` in `ensureTmuxSession`'s claudeArgs (same pattern
   as the inline `--settings` Stop-hook injection). tmux is one long-lived
   process, so the launch prompt carries only static content: role identity +
   the chat-only rule. Per-engagement guidance stays in the per-message
   prompt text.
2. **Define the rule once** as an exported constant (e.g. CHAT_ONLY_RULES in
   hubRouter or a new promptRules.ts) and include it in:
   - `globalRules` inside buildGuidance (reaches every --print engagement),
   - `buildSystemPrompt`,
   - `continueTalking`'s hand-rolled guidance,
   - the tmux launch system prompt (item 1),
   - optionally the triggered work prompt.
3. **Fix Section A contradictions in the same change** (triggered vs
   globalRules, CHANNEL_REPLY vs auto-post, unify SKIP phrasing) — a new rule
   layered onto contradictory instructions is unreliable.
4. **Boundary (be honest about it):** a system prompt stops MODEL-generated
   menus (AskUserQuestion-style). It cannot prevent HARNESS-generated TUI
   dialogs (permission prompts, trust dialogs, plan-mode approval) — those
   remain covered by tmux auto-approve patterns, the choice-menu
   auto-resolver, and the Stop-hook sentinel.

2. Small behavioral gaps: maxTurns/bare on paths lacking them (A2, A5, A6);
   decide whether local-machine --print should honor sshOpts.
